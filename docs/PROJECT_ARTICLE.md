# 从一个本地 Agent 到可扩展插件平台：Plugin Harness 实践笔记

## 背景：为什么做这个项目

我想回答一个看起来简单、实际上很容易含糊其辞的问题：插件机制是不是真能扩展宿主，而不是把插件功能伪装成主程序里的分支？

很多项目会提供一个“插件接口”，但 Agent 循环、工具调用、Provider、权限和界面仍然集中在宿主里；第三方功能只是以硬编码方式接在特定位置。Plugin Harness 希望从架构上证明另一件事：宿主只负责稳定、通用的机制，具体能力由外部插件声明和实现。

这个项目是一个本地运行的 AI Agent Harness，提供 CLI 和本地 Web 应用，零 npm 第三方依赖。它的目标不是成为功能最多的 Agent，而是建立一套可以直接验证的插件边界：

- 主程序不内置天气、笔记、隐私治理或大模型能力；
- 工具、数据拦截 Hook 和 Provider 都来自独立插件；
- 插件在独立进程中运行；
- 用户逐项授予权限，宿主代理文件、网络和密钥；
- 插件崩溃、超时或版本不兼容时，宿主仍可继续运行。

## 从概念 Harness 说起：它解决的不是一次模型调用

如果把一次大模型请求称为“大脑的一次思考”，那么 Harness 更像大脑之外的身体、神经系统和操作规程。Harness 要解决的不是如何生成下一段文本，而是：

- 模型可以使用哪些工具；
- 工具的参数是否合规；
- 数据应在哪个环节被修改、拦截或审计；
- 工具调用超时或崩溃后如何恢复；
- 外部能力能否热更新、被撤权或被熔断；
- 用户是否能在运行过程中观察到系统状态；
- 最终回答是否经过了任何可执行的事实验证。

因此，简单的 `LLM + function calling` 只是一个最小模型循环；Agent Harness 是围绕这个循环建立的生命周期和控制系统。它可能包含会话、工具注册、记忆、检索、权限、进程监管、事件流、错误恢复、日志审计和测试真值。

模型擅长理解意图、规划步骤和组织自然语言，但不应该成为唯一的权限仲裁者、进程管理器或事实校验器。Harness 永远需要知道“什么能力是真的可用”“调用结果是不是真发生了”“哪些数据允许进入模型”。这也是我理解“表层编排会被模型内化，而底座不会消失”的原因：

- 模型可以越来越擅长选择工具，但不能替代工具调用是否越权；
- 模型可以越来越擅长修复错误，但不能替代进程超时与回收；
- 模型可以生成看似可靠的结论，但不能替代文件读取、测试执行或网络状态等可验证证据；
- 模型可以理解一个工作流，但不能替代状态机决定插件是应该重启、热更新还是熔断。

2025–2026 年的 Agent 工程体系，本质上是在把不确定的模型决策放进确定性的执行边界中。Plugin Harness 正是围绕这一点建立的一个最小但完整的实验平台。

## 项目如何对应 Agent 工程体系

| 概念 | 它解决什么问题 | 在 Plugin Harness 中的落点 |
|---|---|---|
| Harness | 给模型调用和生命周期提供执行底座 | `Host`、Agent 循环、进程监管、权限代理、日志审计、状态协调 |
| Plugin | 让能力脱离宿主主程序独立存在 | 一个插件对应一个进程、清单和入口，由 tools、hooks、providers、settings 组成 |
| MCP | 用标准化协议暴露工具、资源和能力 | 项目没有实现完整 MCP，而是实现了类似的 JSON-RPC 能力边界；本质上是把宿主、插件和外部能力解耦 |
| Skill | 给模型提供可复用、可组合的能力描述 | 当前等价于插件声明的 tool + manifest；未来可把工作流或领域操作进一步封装为 Skill |
| Hook | 在正常流程节点前后插入横切逻辑 | 用户消息、工具调用前后等 Hook；支持优先级和 `open/closed` 失败策略 |
| Agentic RAG | 模型先检索，再基于证据生成答案，必要时继续检索或调用工具 | 工作区笔记的检索工具提供了本地 RAG 基础；Agent 可多轮读取、调用和追加内容 |
| 事件驱动编排 | 让状态变化、进度和生命周期以事件流传递 | IPC 消息、Host EventEmitter、日志、SSE、进度和插件状态事件 |
| 自校验熔断 | 不只捕获异常，还要判断何时隔离失败组件 | 超时计数、退避重启、OOM识别、连续崩溃熔断、closed Hook 阻断 |
| 可执行真值验证 | 用测试或工具返回的事实，而不是模型自我评价证明结果 | 参数 schema、契约检查、node:test、混沌猴故障、审计日志、真实接口验收 |

这张表不是把项目硬说成了完整 MCP 或完整 RAG 平台，而是把相近概念落在现有最小实现上。面试时可以明确区分“已经实现”和“可以继续演进”：

- 已实现的是插件化工具、Hook、Provider、进程隔离、JSON-RPC 和事件流；
- 未实现完整 MCP 传输层、资源订阅、远程 Skill 注册表或向量检索；
- 但项目已经具备向 MCP、Skill 和 Agentic RAG 演进所需的边界。

## MCP、Plugin 和 Skill 的关系

MCP 的核心价值，是让工具提供方和宿主之间有一套相对标准的能力发现与调用协议。Plugin Harness 的内部 JSON-RPC 完成了相似但更小的目标：宿主先读取清单，再用 `activate`、`tool.invoke`、`hook.run`、`provider.complete` 等方法与插件通信。

区别在于，MCP 通常强调跨进程、跨语言或跨服务的标准工具协议；这里的协议运行在宿主进程与插件 Node 子进程之间，方法和传输形式由项目自定义。它可以成为类 MCP 边界，但不应直接称为完整 MCP 实现。

Skill 与 Plugin 也不能画等号：

- Plugin 是部署、隔离、生命周期和权限的容器；
- Tool 是单个可调用的能力；
- Skill 是面向任务的一组指令、知识、约束和可调用工具；
- MCP 可以作为不同组件之间的互操作协议。

例如，未来可以把“整理工作区笔记”封装成一个 Skill：它包含领域规则、检索顺序、写入约束、失败处理和需要调用的 `workspace-notes.search/read/write` 工具。宿主仍负责进程、权限和审计，Skill 执行时再声明依赖哪些工具。这个项目已有最小前置条件：清单中的工具描述、参数 schema 和配置项都能让宿主发现能力。

## Agentic RAG：检索不是单独的向量库功能

传统 RAG 通常是“生成查询 → 检索文档 → 拼进提示词 → 一次生成”。Agentic RAG 把检索变成 Agent 工作流中的一个可观察、可重复、可终止的决策：

1. 模型根据任务决定是否检索；
2. 工具执行检索并返回证据；
3. 宿主把证据加入下一轮消息；
4. 模型继续读、比较或写入；
5. 如果证据不足、调用失败或超出步数限制，系统明确停止或报错。

这个项目里的工作区笔记插件就是一个轻量本地 RAG 工具集：

- `list` 提供证据集合；
- `search` 提供关键词检索；
- `read` 提供完整上下文；
- `write` 把经过检查的结论写回工作区。

它不是向量检索，也没有重排序和分块流水线，但它已经体现了 Agentic RAG 的关键控制：检索是工具，不是宿主硬编码的背景知识；调用前校验参数；调用后经过 Hook；结果进入会话；失败会作为结构化错误反馈给下一轮模型。

这使得项目可以自然演进为更完整的 RAG：

- 增加文档索引插件，提供 `index/search/chunk` 工具；
- 检索结果携带来源、分数、更新时间和内容片段；
- Hook 对引用来源做完整性或敏感内容检查；
- Agent 要求回答时引用证据；
- 对“来源是否支持结论”进行独立校验；
- 超过检索步数或证据置信度不足时停止，不输出伪确定答案。

真正的 Agentic RAG 应当保留证据和调用链，而不只是把检索文本塞进 prompt。这个项目的会话 transcript 已经保留了工具调用、工具结果、耗时、插件和 Hook 信息，为以后加入引用溯源和可信度验证提供了基础。

## 事件驱动编排：状态变化先变成事件，再变成界面

Agent Harness 不应该只有方法调用，还应该暴露执行过程中的状态变化。Plugin Harness 使用四个相互衔接的事件层：

- IPC 接收插件的 `log`、`progress` 和请求；
- `PluginProcess` 发出 `starting/running/crashed/failed/stopped` 生命周期状态；
- `Host` 将插件状态、工具进度、日志和状态变化统一发到 `EventEmitter`；
- 本地 Web 服务通过 SSE 推送到浏览器。

这里的事件不只是“用户看到进度”，它也用于行为协调：

- 用户修改配置后，`state.json` 变化会触发宿主 `reconcile()`；
- 插件启动、热更新或退出时，`listTools()` 的可用性随状态变化；
- CLI 修改状态后，宿主监听文件变化并同步；
- Agent 调用工具时，工具调用、Hook note、工具结果和完成事件进入 transcript；
- 插件日志和审计记录同样带有插件 ID、会话或主机等上下文。

相比把所有状态塞进同步返回值，事件流使长任务、进度、插件故障和多会话可以解耦。宿主仍是事实仲裁者，但用户界面并不需要轮询插件进程的内部实现。

## 自校验和熔断：不是假装出错可以容忍

项目的自校验首先发生在调用之前：

- 清单中的工具必须有实现；
- 输入要符合 JSON schema；
- `apiVersion` 和 `engines.harness` 要满足兼容范围；
- 权限只能来自清单声明并与用户授权取交集；
- Hook 和 Provider 结果必须经过宿主的失败策略处理；
- 工具返回过大时会截断，避免污染下一轮上下文。

调用之后，宿主会记录成功、失败、超时、耗时、会话来源和审计事件。安全 Hook 使用 `failMode: closed` 时，Hook 失败、超时或插件不可用都不会被解读成“检查通过”；操作直接被阻止。只有明确设计为提示性检查的 Hook 才使用 `open`。

熔断不是只在进程崩溃后重试。项目区分了不同故障：

- 激活失败：不重试，用户修复清单或实现后手动重启；
- 工具超时：本次调用失败，并可以取消插件调用；
- 连续超时：强制回收卡住的进程；
- 崩溃或 OOM：退避重启；
- 短时间多次崩溃：熔断并停止自动重启；
- Provider 不可用：保留合法历史，并从外部结果中明确提示修复方式。

这里体现了一个重要观点：重试不是无条件的。不同错误应有不同策略，只有瞬时故障适合退避重试；确定性配置错误、权限拒绝和安全拦截不能靠重试解决。

## 可执行真值验证：用运行结果证明，而不是只看描述

“可执行真值验证”意味着，系统中至少有一部分结论能由确定性程序、测试或外部事实证明，而不是由模型表述证明。

在这个项目里，真值来自多个层次：

- 清单契约由解析器和激活阶段验证；
- 参数由宿主 schema 校验；
- 文件越权由 Node 权限模型直接拒绝；
- 网络主机和密钥权限由宿主代理逐次校验；
- 崩溃、超时、OOM 和熔断由真实进程状态验证；
- UI 安全由 Host、Origin、token 和 CSP 测试验证；
- 模型能否调用工具由端到端天气、笔记、Provider 验证；
- 隐私脱敏和密钥写入阻断由工具与 Hook 测试验证。

`36/36` 的测试通过并不是故事的重点，重点是测试覆盖的是哪些边界：

- 错误插件能否拖垮其他插件；
- 越权访问能否被运行时拒绝；
- 权限撤销能否立即改变进程行为；
- Hook 抛错时是应跳过还是阻止；
- 崩溃是应该重启、熔断还是等待人工修复；
- 更新是否会在新权限批准前安装运行；
- 事件流是否能够让 CLI 与 Web 收敛到同一状态。

未来可以进一步把可执行真值做得更强，例如：

- 为工具结果附加来源或校验规则；
- 在写入前执行文件内容检查；
- 对模型答案中的引用逐条回看工具证据；
- 保存测试基线和回放对话；
- 用独立校验插件判断结论是否符合预期；
- 把日志与审计生成可追踪的执行证据。

## 怎么证明宿主被真正扩展了

最直接的证据，是禁用一个插件时观察宿主能力是否随之消失。

`workspace-notes` 提供列出、搜索、读取和写入笔记的工具；`weather` 提供天气查询工具；`pii-guard` 在用户消息和工具结果经过宿主时做脱敏与拦截；`rule-router` 和 `openrouter-provider` 分别提供离线 Provider 与真实大模型 Provider。

其中，最重要的一个实验是切换 Provider：

- 使用 `rule-router` 时，可以用正则和确定性规则完成本地对话和工具调用；
- 使用 `openrouter-provider` 时，同一套工具调用协议可以接入支持工具调用的大模型；
- 两个 Provider 都只是宿主发现并加载的插件，不需要改 Agent 主循环。

这说明宿主真正拥有的是“运行一次 Agent 对话”的能力，而不是某一种模型或某一组固定工具。Provider 和工具都通过约定注册；Agent 循环只负责选择 Provider、生成调用、执行工具和处理返回结果。

另外，`pii-guard` 使用的是纯 Hook 插件、零权限，却能横切修改和拦截整个数据流。它既可以在输入发给模型前脱敏，也可以在工具调用前后检查和改写数据。这类能力如果写进 Agent 的主分支，就会成为复杂的特殊逻辑；放进插件后，宿主只保留 Hook 管线和失败策略。

## 宿主与插件的边界

整个系统可以概括为：

```text
浏览器 / CLI
      |
      v
宿主 Host
- Agent 循环
- 工具调度与参数校验
- Hook 管线
- 插件进程监管
- 网络与密钥代理
- 日志和审计
- 声明式 Web 展示
      |
      | JSON-RPC IPC
      v
独立插件进程
- 工具实现
- Hook 实现
- Provider 实现
- 插件配置
```

宿主提供机制，插件提供能力。插件通过 `plugin.json` 声明工具、Hook、Provider、配置项和所需权限；宿主在执行任何插件代码之前就能展示插件做什么、需要什么、是否兼容。

| 边界对象 | 宿主负责 | 插件可以做的事 |
|---|---|---|
| 工具 | 参数校验、超时、审计、结果截断、调度工具和 Hook | 声明工具名称与输入 schema，实现 `tool.invoke` |
| 数据治理 | Hook 顺序、失败策略、跨会话传递和回滚 | 改写或拦截消息、工具输入和工具结果 |
| Provider | 保持 Agent 循环和模型调用协议 | 实现 `provider.complete`，决定如何路由和调用模型 |
| 配置 | 读取、持久化、热更新和表单展示 | 声明配置项、读取配置并响应配置变更 |
| 文件 | 解析授权路径、启动 Node 文件沙箱 | 只能访问宿主授予的工作区或私有数据路径 |
| 网络 | 主机白名单、重定向检查、响应上限和审计 | 使用宿主代理发起 HTTP 请求 |
| 密钥 | 保存、授权检查和明文下发 | 通过宿主 API 请求已授权密钥 |
| UI | 渲染页面、处理认证、展示对话与日志 | 声明表格、卡片、快捷操作和设置项，不注入 JS |

数据不是由宿主直接暴露成共享对象，而是通过 JSON-RPC 请求和响应传递。宿主调用插件时发送方法名、参数和调用 ID；插件向宿主请求网络或密钥时，由宿主校验并返回结果。工具结果既包含文本，也可以包含结构化数据和声明式 `display` 描述。宿主负责渲染，插件不能把任意组件或脚本塞进页面。

## 稳定性：插件失败不能等于宿主失败

我选择了“每个插件一个 Node 子进程”作为隔离模型，而不是同进程加载，也不是把插件放进 Worker 线程。

同进程加载开发成本最低，但只要插件抛出未捕获异常、进入无限循环或耗尽内存，就可能拖垮宿主。Worker 线程也无法提供完整的进程级权限边界；一个文件级崩溃或堆问题仍可能影响宿主进程。子进程则让插件拥有独立生命周期，宿主可以终止、重启或熔断某个插件，而无需关闭整个 Agent。

具体机制包括：

- 激活、工具调用、Hook 和 Provider 都有超时；
- 两次连续工具超时后强制回收卡死进程；
- 插件崩溃后按退避策略自动重启；
- 60 秒内连续崩溃三次会触发熔断，需要用户手动重启；
- 激活失败是确定性错误，不进入无限重启；
- 每个插件配置堆内存上限，OOM 会被识别为插件故障；
- Agent 单轮最多执行八步，避免无限工具循环；
- 工具结果超过上限时截断，避免一次大响应冲爆上下文和界面；
- `state.json` 是单一状态源，宿主用它协调期望状态和实际进程状态。

当插件崩溃时，宿主保留最近一次错误、错误位置、stderr 尾部和生命周期状态，并通过状态卡片和日志告诉用户发生了什么。手动重启不会影响其他插件。

在兼容性方面，清单声明 `apiVersion` 和宿主版本范围。插件可以安装，但如果宿主版本不兼容或清单契约无效，就不能启用。更新时如果新增权限，宿主会保留旧版本和旧权限，等待用户逐项批准；拒绝新增权限后，插件不会悄悄获得更多能力。

## 权限与安全：不只靠“信任插件”

权限是插件声明、用户授予、宿主强制执行三者共同组成的。

清单可以申请：

- `fs.read`：读取指定目录；
- `fs.write`：写入指定目录；
- `network`：访问指定主机；
- `secrets`：读取指定名称的密钥。

用户安装或更新时能看到每项权限的用途和风险等级。用户可以逐项取消，撤销后宿主会以新的权限重启进程。插件不能授予自己没有在清单中声明的权限。

Node 24 的 `--permission` 模型负责进程内文件、子进程、Worker 和原生扩展限制。宿主启动插件时只允许读取运行时、插件目录、插件私有数据和已授予路径，并只允许写入插件私有数据和已授予目录。

网络和密钥没有直接交给插件进程：

- 插件的全局 `fetch` 被替换成宿主代理；
- 宿主逐个校验目标主机名，每次重定向也重新校验；
- 未授权主机和密钥都会返回明确错误，并写入审计日志；
- 插件进程没有继承宿主环境变量，密钥也不能通过环境变量偷取；
- 密钥文件保存为 `0600`，但密钥一旦授予，宿主无法继续约束插件拿到明文后做什么。

本地 Web 服务也有独立防线：只监听 `127.0.0.1`，启动时生成一次性 token，并校验 Host、Origin 和 CSP。插件提供的内容只按文本渲染，不允许提交任意 HTML 或脚本。

## 一次安全边界演示

混沌猴插件用故障工具验证了这些边界：

- 尝试读取 SSH 密钥、`/etc/passwd` 或写 `/tmp` 时，运行时拒绝越权；
- 未授权网络主机和原始 socket 会被拦截；
- 环境变量中没有密钥；未授权密钥请求会被拒绝并审计；
- 启动子进程会触发 `ERR_ACCESS_DENIED`；
- 挂起工具超时后，进程仍可继续处理其他调用；
- 内存超限只终止插件，宿主和其他插件继续运行；
- 连续崩溃触发熔断，手动重启后恢复。

这些实验说明隔离不是单纯的“进程分开”，而是一组叠加的机制：清单声明、用户授权、运行时沙箱、宿主代理、进程监管和审计共同构成边界。

## 我学到了什么

### 1. 插件平台首先是状态机，而不是动态加载器

真正麻烦的不是让插件执行代码，而是让“期望状态”和“实际状态”保持一致。清单、版本、授权、配置和进程状态都可能变化；宿主必须决定是热更新、重启、停止还是拒绝启用。

`state.json` 加上 `reconcile()` 让 CLI 和 Web 可以共享同一份状态：无论状态从哪里修改，宿主都负责把插件进程收敛到一致状态。这个模式比直接在每个命令里启动或停止进程更可靠。

### 2. 宿主与插件最重要的接口是“错误边界”

仅定义成功返回是不够的。超时、崩溃、未授权、版本不兼容、无效输入、Hook 阻止和 OOM 都必须有稳定的错误形状，并能转成用户能理解的说明。

最有价值的不是替插件掩盖错误，而是让宿主保留插件崩溃时的证据、上下文和恢复入口。

### 3. 权限不是只在安装时生效

权限必须贯穿整个运行链：清单声明权限、用户授予权限、进程启动时注入有效权限、宿主代理每次请求、撤销后重启进程、操作结果写入审计日志。

如果只是在安装页展示同意，而运行时不强制执行，那权限就只是免责声明。这里的权限最终变成了进程参数、代理检查和可撤销状态。

### 4. 声明式清单让宿主获得先验能力

清单让宿主在运行插件代码之前就知道工具输入、界面展示、Hook、权限和配置。它同时支持插件发现、权限审批、参数校验、配置表单和兼容性判断。

这是宿主“不写死功能”的关键。宿主不需要知道笔记、天气或隐私规则长什么样，只需要知道插件如何声明和调用这些能力。

### 5. 安全边界必须坦诚说明

这个项目不是绝对沙箱。Node 权限模型能强制文件、子进程和 Worker，但网络隔离仍主要依赖进程内补丁和宿主代理。因此项目明确将它描述为进程内防护，不声称等同于容器或 OS 沙箱。

完全不可信的第三方代码仍需要 macOS `sandbox-exec`、Linux namespaces/seccomp 或容器等下一层防御。没有插件签名、来源校验和远程市场，也不能把它当作公共插件生态的安全基础。

### 6. Harness 的核心价值是确定性的执行契约

通过这个项目，我更加清楚地理解了 Harness 与简单 Agent 框架的区别。简单脚本可以完成一次工具调用，但难以回答以下问题：插件状态何时变化、超时是否会取消调用、权限撤销是否立即生效、结果是否经过安全 Hook、崩溃时是否保留证据。

Harness 的核心不是替模型做所有决策，而是把决策放进可执行契约中。模型负责选择和组织，宿主负责校验、隔离、审计、恢复和状态收敛。这些机制不会因为模型能力增强而自动消失，只会从应用代码向更通用的运行时层移动。

### 7. MCP 是互操作协议，Plugin 是运行边界

MCP 解决的是能力如何跨客户端、服务器和进程描述与调用；Plugin 解决的是能力由谁承载、如何隔离、何时启用和何时熔断。一个系统可以实现类似 MCP 的协议，却没有真正进程隔离；也可以实现强插件边界，却没有标准互操作协议。

这个项目主动选择了后者的核心，然后以 JSON-RPC 模拟了前者最关键的能力发现和双向调用。最重要的收获不是协议名，而是：能力发现、权限、生命周期和调用上下文必须沿着同一条主干传递。

### 8. Skill 是任务知识，不能拿来替代执行约束

Skill 的价值在于把领域指令、参考材料、工具选择和工作流组织成可复用包，但它不能代替宿主限制文件、网络和密钥。一个 Skill 可以告诉模型“先搜索，再读取，再验证”，却不应被赋予绕过文件沙箱的能力。

因此，未来实现 Skill 时应该区分任务语义和运行权限：Skill 声明需要哪些工具和什么时候使用，Plugin/Host 决定工具是否存在、是否授权、是否可用、调用是否成功。这样模型和应用都不会把文本指令误当成安全证明。

### 9. Agentic RAG 应以证据链为一等公民

这个项目让我意识到，RAG 不应只是检索数据库并拼接上下文。好的 Agentic RAG 至少要保留检索工具、来源、调用顺序、失败状态和最终引用；否则回答看似有依据，实际上无法复核。

工作区插件目前使用关键词检索而不是向量检索，但已有的工具 schema、Hook 管线和 transcript 可以演进成证据链。面试中我会强调，这不是因为本项目已经覆盖完整 RAG，而是因为它提供了宿主、检索工具、调用记录和安全边界的完整骨架。

### 10. 可执行验证比模型自评更可信

模型可以判断自己的回答是否流畅，但无法直接证明某个进程是否越权、某个文件是否存在、某次网络请求是否被授权或某个测试是否通过。可执行验证应该由运行时、测试和独立校验提供。

混沌猴、node:test、权限日志、工具审计和真实接口调用，让项目的结论不依赖“看起来能用”。这也是我认为最有价值的面试抓手：展示的不只是代码，而是一个能被独立检查、故障注入和复现验收的系统。

## 验证结果与局限

项目使用 `node:test` 进行自动化验证，覆盖清单契约、版本兼容、权限、沙箱、超时、崩溃、熔断、OOM、Hook、更新审批和 Web 安全。36 个用例在 Node 24.10.0 与 macOS 环境中通过，并结合浏览器和真实天气、OpenRouter 调用做了端到端验证。

目前仍有明确的局限：

- 网络隔离不是 OS 级防护；
- 密钥授予后插件能获得明文；
- 没有插件签名和远程可信来源；
- CPU 没有硬配额；
- 没有第三方插件市场；
- 插件只支持 Node.js；
- 只在 macOS 上完整验证；
- 声明式 UI 不允许插件注入自定义组件。

这些局限不影响项目作为演示，但会决定它能否直接用于不受信任的第三方市场。它最重要的价值，是把“插件机制、隔离、权限、兼容性和恢复”做成可运行、可观察、可验证的系统，而不只是写在文档里的接口承诺。
